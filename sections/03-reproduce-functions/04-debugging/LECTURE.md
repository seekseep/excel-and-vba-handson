## 原因を探す

コードを眺めて見つけられるかもしれませんが、ここでは 3-3 の道具を使って、**実行を途中で止めて、変数の中身を見る** やり方で探します。

1. `total = total + ...` の行にブレークポイントを置く
2. `SumTotalWithBug`（GAS は `sumTotalWithBug`）を実行（GAS は **デバッグ**）して止める
3. 止まったときの `i` と `total` を見る
4. 1 行ずつ進めながら、`i` と `total` がどう変わるかを、3-3 で見た正しい `SumTotal` と比べる

:::notice[ヒント]
3-3 で `SumTotal` を止めたとき、最初の `i` はいくつでしたか？
:::

:::::platform
::::excel
最初に止まったとき、`i` は **3** になっています。データは 2 行目から始まるのに、3 行目から足し始めていたので、2 行目（1,250 円）が足されていなかったのです。

`For i = 3` を `For i = 2` に直して、もう一度実行してください。J2 が 68,580 になれば成功です。

## 原因の探し方を振り返る

今回やったことは、どんなコードにも使えます。

1. **期待と結果のずれを確かめる** — 関数の答え（68,580）と VBA の答え（67,330）が違う。差は 1,250
2. **怪しいところで止める** — 合計を足している行にブレークポイント
3. **変数を見ながら進める** — 正しく動くときと比べて、どこから違うかを探す
4. **直して、もう一度確かめる**

差の 1,250 が 2 行目の金額と同じだと気づければ、止める前に見当が付くこともあります。答えの分かっている問題で練習しておくと、こうした見当の付け方も身につきます。

## これは関数で十分だった

ここまでで、関数で出した答えを VBA でもすべて再現できました。並べてみると、

| | 関数 | VBA |
|---|---|---|
| 書く量 | 式 3 つ | マクロ 3 つ |
| データを直したとき | 自動で計算し直す | もう一度実行する |
| 計算の根拠 | セルに残る | コードを読まないと分からない |

この集計に限っていえば、**関数のほうが向いています**。それでも VBA で書いたのは、ここで使った 3 つの道具が、関数ではできない処理の部品になるからです。

- `Cells(i, 列)` で行を順番に指す
- `For` でくり返す
- `If` で条件に合う行だけを選ぶ

第 5 章では、この 3 つをそのまま使って「顧客ごとに請求書のシートを作り、明細を書き写す」処理を作ります。

### J2 が `0` になります

F 列の金額が空のままです。3-1 の `CalcAmounts` を先に実行して F 列を埋めてから、もう一度試してください。

### AI にコードを見せて直してもらえばよいのでは？

それで直ることも多いです。ただ、AI の答えが合っているかを確かめるのは自分です。デバッガーで「どの行で、変数がいくつだったか」を確かめておけば、AI に正確な情報を渡せますし、返ってきた修正が本当に原因を直しているかも判断できます。

### エラー処理（`On Error`）を書いておけば防げませんか？

今回のバグはエラーにならず、答えが違うだけなので、`On Error` では見つかりません。特に `On Error Resume Next` はエラーを無視して先に進むので、原因を隠してしまいます。「答えが合っているか」を確かめたいなら、`Debug.Assert Range("J2").Value = Range("I2").Value` のように期待する条件を書いておく方法があります（条件が成り立たないと、その行で止まります）。GAS では `if` で比べて `throw new Error(...)` します。

### 「1 行ずれ」のバグを起こしにくい書き方はありますか？

まず、**最初の 1 周と最後の 1 周だけは必ず確かめる** 習慣が効きます。くり返しのバグは、ほとんどが端で起きるからです。ブレークポイントで最初の `i` を見て、`lastRow` の値を見れば、それだけで今回のバグは見つかります。また、`2` のような数をコードのあちこちに書かず、`Const firstRow As Long = 2`（GAS は `const FIRST_ROW = 2;`）のように名前を付けておくと、「見出しは 1 行」という前提が読み取れるようになり、書き間違いにも気づきやすくなります。

### 直したのに、J2 が 67,330 のままです

直したあとに、もう一度マクロを実行しているか確かめてください。VBA が書き込んだ値は、コードを直しただけでは変わりません。また、直したのが `SumTotalWithBug` で、実行しているのが別のマクロ（またはその逆）になっていないかも見てください。

### こういう間違いを、毎回自動で見つける方法はありませんか？

期待する結果と比べる、小さな確認のマクロを書いておく方法があります。たとえば `Debug.Assert Range("J2").Value = Range("I2").Value` は、両方の値が一致しないときにその行で止まります。Windows の VBE なら、Rubberduck というアドインで単体テストを書くこともできます。GAS でも、結果を比べて違えば `throw new Error(...)` で知らせる関数を用意しておけます。

:::
